## 1. 警告が来たときの初動

上から順に見ていくと切り分けが早いです。

### ① GitHub Actions の実行履歴を見る

いま実行中のジョブがあれば、まず待ちます。処理の最中にwatchdogが走って誤警報を出しているだけ、というケースがよくあります（→ [3章](#3-実行時刻と監視時刻のズレ)）。

**警告が出た時点では、まだリトライが残っています。** 11:30の⚠️なら11:45に、12:30の⚠️なら12:45に、cron-job.orgが再実行をかけます。急ぎでなければ、その結果を見てから動くほうが確実です。

### ② 公開ページの `prices.json` の日付を見る

Webだけ今日の日付に更新されていたら、**Instagram投稿だけが失敗した**パターンです。完了マーカーはInstagram投稿の成功後にしか書かれないので、watchdogからは「未配信」に見えます。

`.ig_state.json` を見れば何枚目まで投稿できたか分かります。トークン切れが疑われるときは `check_ig_token.py` のログも確認してください。

### ③ cron-job.org の管理画面を見る

ジョブが失敗していないか、自動的に無効化されていないかを確認します。**PATの期限切れは実際に起きた死因**なので、真っ先に疑うべきポイントです（→ [6章](#6-過去の障害となぜガードが多いのか)）。

### ④ Actions の失敗ログを見る

ここまでで原因が絞れなければ、ステップごとのエラーを追います。よくあるのはJEPXの公表遅延と、Pages反映のタイムアウトです。

### 復旧後、当日分を出し直したいとき

Actionsから `daily-denki-yohou.yml` を手動実行し、`force=true` を指定します。`force` なしだと配信済みガードでスキップされます。

ただしInstagram投稿の途中失敗からの再開なら、`force` は不要です。`.ig_state.json` が進捗を持っているので、通常の再実行で残りの枚数だけが投稿されます。

## 2. 監視（watchdog）の仕組み

`.github/workflows/denki-yohou-watchdog.yml` が、本体とは別枠で毎日 **11:30と12:30（JST）** に `docs/.last_run` を確認します。

| 状態 | 通知 |
|---|---|
| 当日分がまだ未配信 | ⚠️ 警告（原因の当たりどころ付き） |
| 配信済みだが完了が11:00以降 | 🐢 遅延注意 |
| 通常どおり10:48ごろに完了 | 何も言わない |

この監視自体もGitHubのネイティブcronに乗っています。そのためGitHub側が混雑すると、警告そのものが数時間遅れることがあります。「即座に気づく」ではなく「当日中には必ず気づける」ことを目的とした割り切りの設計です。

## 3. 実行時刻と監視時刻のズレ

起動と監視は別々に設定されていて、噛み合っていません。時系列に並べるとこうなります。

| 時刻 | 誰が | 何を |
|---|---|---|
| 10:40 | GitHub cron | 起動（遅延しがち） |
| **10:45** | **cron-job.org** | **起動（本番）** |
| 11:10 | GitHub cron | 起動（配信済みならスキップ） |
| **11:30** | **watchdog** | **確認 → 未配信なら⚠️** |
| 11:40 | GitHub cron | 起動（配信済みならスキップ） |
| **11:45** | **cron-job.org** | **リトライ** |
| **12:30** | **watchdog** | **確認 → 未配信なら⚠️、遅ければ🐢** |
| **12:45** | **cron-job.org** | **リトライ（最後）** |

ここから、紛らわしい挙動が3つ生まれます。

**watchdogは必ず「リトライ待ち」の状態を見ている。** 11:30の確認は11:45の再実行より前、12:30の確認は12:45の再実行より前です。つまり⚠️が出た時点では、まだ打つ手が残っています。「11:30に⚠️ → 11:45で復旧 → 12:30に🐢」と同じ朝に2通飛ぶのは正常な流れです。

**最後のリトライ（12:45）の結果は、watchdogが見ていません。** 12:45以降にwatchdogは走らないので、ここで成否を知らせるのは本体の完了通知（`notify_slack.py`）だけです。12:30の⚠️が最後の警告になるため、**その後に完了通知が来たかどうか**を必ず確認してください。

**Webは公開済みなのに「未配信」扱いになることがある。** 完了マーカーはInstagram投稿の成功後にしか書かれません。Web公開まで成功していてInstagram投稿だけ失敗した日は、watchdog上は未配信のままです。

> 💡 噛み合わせを直すなら、watchdogを12:00と13:00（各リトライの15分後）にずらすのが素直です。そうすればリトライ結果を見てから警告できるので、⚠️の空振りが減ります。現状は「多少の空振りより当日中に気づけること」を優先した割り切りなので、変更する場合は `denki-yohou-watchdog.yml` のcronと、cron-job.org 側の設定を両方見比べて決めてください。

## 4. アラート発火時の手動送信手順

**Slackに通知が来ても、お客様にメールは飛んでいません。** 素材ができただけです。送信は人が中身を確認してから行います。

1. Slack通知のGoogle Driveリンクを開く
2. `_summary.txt` で全エリアの判定と配信対象を確認する
3. 配配メール管理画面にログインする（From＝カスタマー系）
4. 「エリア」セグメントで該当エリアを選ぶ
5. 件名に `<エリア>_<レベル>.txt` の1行目、本文に `<エリア>_<レベル>.html` を貼り付ける
6. テスト配信で表示を確認し、問題なければ本配信

補足が2つあります。価格アラートは配信停止の設定がなく、該当エリア全員に送信する運用です。また、アラート素材はリポジトリにはコミットされません（`.gitignore` 済み）。Driveにあるものが正です。

判定からSlack通知までを本番影響なしで試したいときは、Actionsから `alert-test.yml` を手動実行してください。既定ではダミー価格で必ず発火するテストモードで動き、Instagram投稿もdocsコミットも行いません。

## 5. よくあるトラブル

| 症状 | 対処 |
|---|---|
| watchdogから⚠️が来た | [1章](#1-警告が来たときの初動)の初動へ |
| CSVが見つからない | `python3 scripts/fetch_jepx.py` を実行 |
| `prices.json` が生成されない | JEPXがまだ明日分を公表していない可能性が高い。時間を置けば自動でリトライされる |
| Slack通知が来ない | Webhookの設定を確認し、`notify_slack.py` を単体実行してみる |
| Instagramに投稿されない | `check_ig_token.py` でトークン残日数を、`.ig_state.json` で投稿済み枚数を確認 |
| 同じ内容が何度も投稿された | `concurrency` と `force` の設定を確認（→ [6章](#6-過去の障害となぜガードが多いのか)の3連投事件） |
| 過去の月平均がおかしい | 手で直さず、JEPXから取り直して `--rebuild`（→ [データ方針](architecture.md#6-データ方針過去データを推測で埋めない)） |

## 6. 過去の障害と、なぜガードが多いのか

ワークフローには一見過剰に見えるガードがあります。すべて実際に起きた事故への対策です。初めて触る人ほど「これ消してもいいのでは」と思いがちなので、先に経緯を共有します。

### 3連投事件

以前は `workflow_dispatch` を無条件で素通りさせていました。そこにcron-job.org側の重複ディスパッチが重なり、そのまま複数回投稿されてしまいました。

対策として、手動の強制再配信は `force=true` のときだけ許可し、`concurrency` で同時並走そのものを禁止しています。

### cron-job.orgのPAT期限切れ（2026年7月4日〜）

外部cron側のトークンが切れて配信が止まっていたのに、3日間誰も気づきませんでした。これがwatchdogを新設した直接のきっかけです。

### Slack通知の20分ハング

`notify_slack.py` の通信に `timeout` を指定していなかったため、Slack側の応答待ちで約20分ジョブが固まり、後続処理を巻き添えにしました。

現在は通信自体にタイムアウトを設定し、さらにワークフロー側にも `timeout-minutes: 2` を入れています。

---

こうした経緯があるので、`continue-on-error`・`concurrency`・`if: always()` を「動作に影響なさそうだから」と外さないよう注意してください。

障害とまではいかない細かい仕様変更の記録は [scripts/軽微修正メモ.md](../scripts/軽微修正メモ.md) にあります。

## 7. 環境変数・Secrets 一覧

GitHubの Settings → Secrets and variables → Actions に登録が必要なものです。

| 名前 | 種別 | 用途 |
|---|---|---|
| `IG_ACCESS_TOKEN` | Secret | Instagram Graph API の長期トークン。**約60日で失効**し、14日前から警告が出る |
| `IG_USER_ID` | Secret | InstagramビジネスアカウントID |
| `SLACK_WEBHOOK_URL` | Secret | 日次結果・Instagramトークン警告・watchdog警告の送信先。投稿先は **#kk_でんき予報** |
| `SLACK_ALERT_WEBHOOK_URL` | Secret | 価格アラート発火通知の送信先（上とは別チャンネル） |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` | Secret | Google Drive格納用（キーレス認証） |
| `GCP_SERVICE_ACCOUNT` | Secret | 同上 |
| `ALERT_DRIVE_PARENT_ID` | Secret | アラート素材を置くDriveフォルダの親ID |
| `PAGES_BASE_URL` | Variable | GitHub PagesのURL。Pages反映確認とSlack通知で使う |

投稿先チャンネルはWebhook URLに紐づいています。変更したいときはSlack側のWebhook設定を触ってください。

次の3つは既定値が入っているので、通常は登録不要です。

| 名前 | 既定値 | 用途 |
|---|---|---|
| `ALERT_OUT_DIR` | `_alerts_out` | アラート素材の出力先（`.gitignore` 済み） |
| `IG_TOKEN_WARN_DAYS` | 14 | トークン失効の何日前から警告するか |
| `RENDER_SCALE` | 2 | PNG書き出しの倍率 |

### リポジトリの外にあるもの

引き継ぎのときに見落としやすい管理物が2つあります。

**cron-job.org のアカウント。** 起動時刻の設定と、`workflow_dispatch` を叩くためのGitHub PATがここにあります。

**Meta（Instagram）側のアプリ設定。** 長期アクセストークンの再発行はこちらで行います。

## 8. ローカルでの動作確認

```bash
# JEPXから最新CSVを取得（年度は自動判定、指定も可）
python3 scripts/fetch_jepx.py
python3 scripts/fetch_jepx.py 2025

# 翌日分のprices.jsonを生成
python3 scripts/build_prices.py --require-tomorrow

# history.json（日数は指定可）
python3 scripts/build_history.py --days 90

# 月平均をマージ更新 / 全期間を作り直し
python3 scripts/build_monthly.py
python3 scripts/build_monthly.py --rebuild

# Stories生成〜PNG書き出し
python3 scripts/build_stories.py
python3 scripts/render_png.py stories.html

# 価格アラートの判定だけ試す
# （Slack/Drive の設定がなければ表示のみのdry-runで安全に終わる）
python3 scripts/build_alerts.py docs/prices.json
```

## 9. 用語集

| 用語 | 説明 |
|---|---|
| JEPX | 日本卸電力取引所。電力のスポット市場価格を公表している |
| エリアプライス | 9つのエリア（北海道〜九州）ごとの取引価格 |
| コマ | 30分単位の取引区切り。1日=48コマ |
| 電力年度 | 4月始まり3月終わりの区切り。JEPXのCSVファイル名の単位 |
| 配配メール | お客様への一斉メール配信に使う社外サービス。このリポジトリとは連携しておらず、本文をコピーして手動送信する |
| cron-job.org | 外部のcron実行サービス。本システムの目覚まし時計。設定はリポジトリ外にある |
| 狼少年化 | アラートを出しすぎて重要な通知まで読まれなくなる状態。全顧客プッシュをLv2以上に絞っている理由 |
| テラゾウ | でんき予報のキャラクター。Stories画像やWebページに登場 |
