## 1. 監視（watchdog）の仕組み

`.github/workflows/denki-yohou-watchdog.yml` が、本体とは別枠で毎日 **11:30 JST / 12:30 JST** に `docs/.last_run` を確認します。

- 当日分がまだ未配信 → ⚠️ 警告をSlackへ（原因の当たりどころ付き）
- 配信済みだが完了時刻が11:00以降 → 🐢 遅延注意（通常は10:4x台に完了する想定）
- 通常通り完了していれば何も言わない静かな監視役

この監視自体もGitHubのネイティブcronに乗っているため、GitHub側が混雑すると警告そのものが数時間遅れることがあります。それでも「当日中に必ず気づける」ことを目的として割り切った設計です。

---

## 2. 実行時刻と監視時刻のズレに注意

現状の設計では、**watchdogの1回目（11:30）が、最後の予備cron（11:40）より先に走ります**。このため次の紛らわしい挙動が起こりえます。

1. **⚠️警告のあとに自然復旧するパターン**：cron-job.orgが死んだ朝は、11:30に⚠️未配信警告 → 11:40の予備cronで配信成功 → 12:30に🐢遅延注意、と**同じ朝に通知が2通**飛びます。11:30の⚠️を見ても、まだ11:40の予備が残っていることを知っていれば慌てる必要はありません（12:30の結果を待ってから動けばOK）。
2. **実行中なのに「未配信」と言われるパターン**：GitHubネイティブcronは遅延が常態のため、例えば10:40の予備が実際には11:20頃に始まることがあります。その処理がまだ走っている最中に11:30のwatchdogが `.last_run` を見ると、「未配信⚠️」の誤警報になります。
3. **Webは公開済みなのに「未配信」扱いになるパターン**：完了マーカー（`.last_run`）は**Instagram投稿の成功後にのみ**書かれます。つまりWeb公開まで成功していてもIG投稿だけ失敗した日は、watchdog上は「未配信」です。

> 💡 このズレを解消したい場合は「watchdog 1回目を11:50以降にずらす」か「予備cronの最終を11:20以前にする」のどちらかで整合が取れますが、現状は「多少の誤警報より、当日中に必ず気づけること」を優先した割り切りです。変更する場合は両ワークフローのcron設定をセットで見直してください。

## 3. ⚠️警告が来たときの初動

次の順で確認すると切り分けが早いです。

1. **GitHub Actionsの実行履歴**：いま実行中のジョブがないか。あれば待つ（上記ズレ2のパターン）。11:30の1回目警告なら、11:40の予備cronが残っているのでいったん12:30の結果を待つ選択もあり
2. **公開ページの `prices.json` の日付**：Webだけは今日の日付に更新済みか。更新済みならIG投稿のみ失敗のパターン（ズレ3）。`check_ig_token.py` のログや `.ig_state.json` で何枚目まで投稿できたかを確認
3. **cron-job.orgの管理画面**：ジョブが失敗・自動無効化されていないか。**PAT（トークン）の期限切れが過去の実績ある死因**（[6章](#6-過去の障害となぜガードが多いのか)）
4. **Actionsの失敗ログ**：JEPX取得失敗（公表遅延）、Pages反映タイムアウトなど、ステップごとのエラーを確認

復旧後に当日分を出し直したいときは、Actionsから `daily-denki-yohou.yml` を手動実行し、`force=true` を指定します（`force`なしだと配信済みガードでスキップされます）。ただし`.ig_state.json`が進捗を持っているので、IG途中失敗からの再開なら`force`は不要で、通常の再実行で残り枚数だけ投稿されます。

## 4. アラート発火時の手動送信手順

アラートは「発火の検知・素材作成・社内共有」までは自動、「お客様への実配信」は手動です。**Slackの通知が来ても、自動でお客様にメールが飛んでいるわけではありません。**

1. Slackの発火通知に付いているGoogle Driveリンクを開く（`_alerts_out/<日付>/` の内容がアップロードされています）
2. `_summary.txt` で全エリアの判定と配信対象を確認
3. 配配メール管理画面にログイン（From＝カスタマー系）
4. 「エリア」セグメントで該当エリアを選択
5. 件名 = `<エリア>_<レベル>.txt` の1行目、本文 = `<エリア>_<レベル>.html` をHTMLメールエディタに貼付
6. テスト配信で表示確認 → 内容に問題ないことを確認した上で本配信

※価格アラートは配信停止なし・該当エリア全員へ送信する運用です。
※アラート素材の出力先はリポジトリにはコミットされません（`.gitignore`済み）。Driveが正です。

アラートの判定→Drive→Slackだけを本番影響なしで試したい場合は、Actionsから `alert-test.yml` を手動実行してください（既定ではダミー価格で必ず発火するテストモード。Instagram投稿・docsコミットは一切行われません）。

## 5. よくあるトラブルシューティング

| 症状 | まず確認すること |
|---|---|
| watchdogから⚠️が来た | [3章](#3-️警告が来たときの初動)の初動手順へ |
| CSVが見つからないと言われる | `python3 scripts/fetch_jepx.py` を実行して `data/spot_summary.csv` を作る |
| `prices.json` が生成されない | `build_prices.py --require-tomorrow` の実行ログを確認。JEPX側に「明日分」がまだ公表されていない可能性が高い（時間を置いて自動リトライされる） |
| Slack通知が来ない | `SLACK_WEBHOOK_URL` / `SLACK_ALERT_WEBHOOK_URL` の設定を確認し、`python3 scripts/notify_slack.py` を単体実行してみる |
| Instagramに投稿されない | まず `check_ig_token.py` でトークン残り日数を確認。`.ig_state.json` を見て、どの枚数まで投稿済みかも確認する |
| 同じ内容が何度も投稿された | `concurrency` 設定と `force` 入力が意図通りか確認。[6章](#6-過去の障害となぜガードが多いのか)の3連投事件と同じパターンの可能性 |
| 過去の月平均がおかしい | 手で `monthly.json` を直さない。[architecture.md のデータ方針](architecture.md#6-データ方針過去データを推論で埋めない)の手順でJEPXから取り直して `--rebuild` |

## 6. 過去の障害と、なぜガードが多いのか

ワークフローには一見過剰に見えるガードがいくつもありますが、すべて実際に起きた事故への対策です。初めて触る人ほど「これ、消してもいいのでは」と思いがちな箇所なので、先に経緯を共有します。

- **3連投事件**：以前は `workflow_dispatch` を無条件で素通りさせていたため、外部cronサービス（cron-job.org）側の重複ディスパッチがそのまま複数回投稿につながってしまいました。対策として、手動の強制再配信は `force=true` のときだけ許可し、`concurrency` で同時並走そのものを禁止しています。
- **cron-job.orgのPAT期限切れ事件（2026年7月4日〜）**：外部cron側のトークンが切れて配信が止まっていたのに、3日間誰も気づきませんでした。これがwatchdogワークフローを新設した直接のきっかけです。
- **Slack通知の約20分ハング**：`notify_slack.py` 内の通信に`timeout`を指定していなかったため、Slack側の応答待ちで約20分ジョブが固まり、後続処理を巻き添えにしたことがあります。現在は通信にタイムアウトを設定した上で、ワークフロー側にも`timeout-minutes: 2`を追加しています。

こうした経緯があるため、`continue-on-error`・`concurrency`・`if: always()` などの指定を「動作に影響なさそうだから」と安易に外さないよう注意してください。

障害とまではいかない細かい仕様変更の記録（円表記の統一、しきい値の一元管理など）は [scripts/軽微修正メモ.md](../scripts/軽微修正メモ.md) に残っています。

## 7. 必要な環境変数・Secrets 一覧

GitHubリポジトリの Settings → Secrets and variables → Actions に登録が必要なものです。

| 名前 | 種別 | 用途 |
|---|---|---|
| `IG_ACCESS_TOKEN` | Secret | Instagram Graph API 長期アクセストークン（**約60日で失効**。失効14日前からSlack警告が来る） |
| `IG_USER_ID` | Secret | InstagramビジネスアカウントID |
| `SLACK_WEBHOOK_URL` | Secret | 日次結果通知（「☀️ 配信処理完了」）・IGトークン失効警告・watchdog警告の送信先。**実際の投稿先は #kk_でんき予報**（Webhookにチャンネルが紐づいているため、変更はSlack側のWebhook設定で行う） |
| `SLACK_ALERT_WEBHOOK_URL` | Secret | 価格アラート発火通知の送信先（上とは別チャンネル） |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` | Secret | Google Drive格納用（Workload Identity・キーレス認証） |
| `GCP_SERVICE_ACCOUNT` | Secret | 同上 |
| `ALERT_DRIVE_PARENT_ID` | Secret | アラート発火物を格納するGoogle Driveフォルダの親ID |
| `PAGES_BASE_URL` | Variable | GitHub PagesのURL（例: `https://tera-energy-jp.github.io/tera-denki-yohou`）。Pages反映確認とSlack通知に使用 |

補足として、以下はワークフロー内で自動的に設定される値・任意の上書き用変数なので、通常は登録不要です。

| 名前 | 既定値 | 用途 |
|---|---|---|
| `ALERT_OUT_DIR` | ワークスペース直下 `_alerts_out` | アラート発火物の出力先（`.gitignore`済み） |
| `IG_TOKEN_WARN_DAYS` | 14 | トークン失効の何日前から警告するか |
| `RENDER_SCALE` | 2 | PNG書き出しの倍率（等倍にしたい場合は`1`を指定） |

このほか、**リポジトリ外の管理物**が2つあります。担当引き継ぎ時は所在確認を忘れずに。

- **cron-job.org のアカウント**と、そこに登録しているGitHubのPAT（workflow_dispatch呼び出し用）。発火時刻の設定もここにある
- **Meta（Instagram）側のアプリ設定**。長期アクセストークンの再発行はこちらで行う

## 8. ローカルでの動作確認

```bash
# JEPXから最新CSVを取得（年度は自動判定、指定も可）
python3 scripts/fetch_jepx.py
python3 scripts/fetch_jepx.py 2025

# 翌日分のprices.jsonを生成
python3 scripts/build_prices.py --require-tomorrow

# 過去180日／指定日数のhistory.json
python3 scripts/build_history.py --days 90

# 月平均をマージ更新 / 全期間を作り直し
python3 scripts/build_monthly.py
python3 scripts/build_monthly.py --rebuild

# Stories生成〜PNG書き出し
python3 scripts/build_stories.py
python3 scripts/render_png.py stories.html

# 価格アラートの判定だけ手元で試す（Slack/Drive設定が無ければ表示のみのdry-runで安全に終わる）
python3 scripts/build_alerts.py docs/prices.json
```
