## 1. 何がきっかけで動くか

本体のワークフローは `.github/workflows/daily-denki-yohou.yml` です。これを起動するきっかけが4つあります。

| きっかけ | タイミング（JST） | 位置づけ |
|---|---|---|
| cron-job.org が `workflow_dispatch` を叩く | 10:45 / 11:45 / 12:45 | **実運用の主役** |
| GitHub Actions の `schedule` | 10:40 / 11:10 / 11:40 | 予備 |
| `data/spot_summary.csv` への push | CSVを手で差し替えたとき | 手動フォールバック |
| 手動 `workflow_dispatch` | 人がボタンを押したとき | `force=true` で強制再配信 |

主役が外部サービスなのは、GitHubのネイティブcronが数十分ずれることがあるためです。時刻の正確さを外部に任せ、GitHub側は「cron-job.orgごと落ちたとき用の保険」として3回に分けて仕掛けてあります。実績では10:48ごろに完了しているので、普段は cron-job.org の10:45が仕事をしています。

> ⚠️ cron-job.org 側の時刻設定は**このリポジトリには存在しません**。上の10:45／11:45／12:45は管理画面で確認した値です。管理画面で変更するとドキュメントとズレるので、変えたときはここも直してください。

### 二重配信を防ぐ仕組み

同じ日に複数のきっかけが発火しても、二重投稿にはなりません。ガードが2段構えになっています。

ひとつは `docs/.last_run` です。ここに今日の日付が書かれていれば、`guard` ジョブが後続をすべてスキップします。もうひとつは `concurrency` 設定で、そもそも同時実行そのものを禁止しています。

どちらも過去の事故を受けて入れたものです（→ [障害の履歴](runbook.md#6-過去の障害となぜガードが多いのか)）。

## 2. 本体処理の流れ

`build-and-notify` ジョブの中身です。

⓪①②…や `①'`・`④-A` といった番号は、ワークフローのステップ名にそのまま付いています。`daily-denki-yohou.yml` を開いて番号で検索すれば、該当箇所にすぐ飛べます。

### 第1段階：データを作る

| # | やること | 失敗したら |
|---|---|---|
| ⓪ | `fetch_jepx.py` でJEPXから最新CSVを取得 | 🛑 以降すべて止まる |
| ① | `build_prices.py --require-tomorrow` で `prices.json` を生成 | 🛑 止まる（これは意図的、後述） |
| ①' | `build_history.py` で `history.json`（最大180日・当年度内）を生成 | ⏭ スキップして続行 |
| ①'' | `build_monthly.py` で `monthly.json`（月平均）を更新 | ⏭ スキップして続行 |

`history.json` と `monthly.json` はWeb表示の補助データなので、作れなくても当日の配信は続けます。

### 第2段階：画像を作る

| # | やること | 失敗したら |
|---|---|---|
| ② | `build_stories.py` で `stories.html` を生成 | 🛑 止まる |
| ③ | `render_png.py` でPNGを書き出し（スライドの数だけ） | 🛑 止まる |
| ④ | 成果物を `docs/` に配置 | 🛑 止まる |

書き出す枚数は固定ではなく、`stories.html` の中にある `.slide` 要素の数だけ生成されます。つまり `build_stories.py` でスライドを増やせば、PNGも自動的に増えます。

> ⚠️ ワークフローのステップ名は「③ PNG（5枚）を書き出し」で固定されていますが、実際の枚数はスライド数に応じて変わります。名前が実態に追いついていないだけで、動作に問題はありません。

### 第3段階：価格アラート（本体と並行）

ワークフロー上は `④-A` 〜 `④-D` という名前の4ステップです。

| # | やること | 失敗したら |
|---|---|---|
| ④-A | `build_alerts.py` で高騰を判定し、発火した日だけメール素材を `_alerts_out/` に出力 | ⏭ スキップして続行 |
| ④-B | Google Cloud の認証（Workload Identity・キーレス） | ⏭ スキップして続行 |
| ④-C | `upload_alerts_drive.py` で素材をGoogle Driveへ格納 | ⏭ スキップして続行 |
| ④-D | `notify_alert_slack.py` でアラート用チャンネルへ通知 | ⏭ スキップして続行 |

アラートは本体から独立した枝です。4つとも `continue-on-error: true` が付いているので、ここが全滅してもWebとInstagramの配信は最後まで走りきります。

発火しなかった日は④-Aが何も出力しないため、④-C以降は実質何もせずに終わります。

### 第4段階：公開する

| # | やること | 失敗したら |
|---|---|---|
| ⑤ | `docs/` と CSV をコミット＆push（＝Pages公開） | 🛑 止まる |
| ⑥ | 公開URLの `prices.json` が更新されたか確認（最大5分待つ） | 🛑 止まる |

### 第5段階：投稿して記録する

| # | やること | 失敗したら |
|---|---|---|
| ⑦ | Instagramトークンの残り日数をチェック | ⏭ 警告を出すだけ |
| ⑧ | Instagram Stories へ投稿 | 🛑 ⑨に進まない＝翌回リトライ対象 |
| ⑧' | `.ig_state.json` に投稿済み枚数を保存 | 1枚ずつ記録するので途中から再開できる |
| ⑨ | `docs/.last_run` に本日日付を記録 | ここまで来て初めて「今日は完了」 |
| ⑩ | Slack #kk_でんき予報 へ結果を通知 | ⏭ 何があっても必ず飛ばす |

⑨のマーカーは**Instagram投稿が成功したあとにしか書かれません**。Web公開まで終わっていてもInstagram（IG）投稿だけ失敗した日は、システム上は「未完了」の扱いになります。

⑩は `if: always()` と `continue-on-error: true` と2分タイムアウトの3点セットで、前段が何であれ必ず通知を飛ばします。

### ①がなぜ「意図的に失敗する」のか

`--require-tomorrow` は「CSVの最新日」ではなく「明日（JST）の行が存在するか」を要求します。JEPXの公表が遅れて明日分がまだ無いときは、ここでエラーにして止めます。

古いデータをうっかり配信しないためのガードです。止まってもマーカー（⑨）は書かれないので、次の予備cronが自動でリトライしてくれます。

## 3. 生成されるファイルの中身

毎日コミットされるファイルの構造です。Webページはこれらを読んで描画しているので、`docs/index.html` を触るときは実質ここがAPI仕様になります。

### `docs/prices.json` — 翌日分の価格

いちばん重要なファイルです。翌日1日分だけを持ちます。

```jsonc
{
  "date_raw":   "2026/08/29",          // 対象日（機械可読）
  "date_label": "2026年8月29日(土)",    // 表示用
  "unit":  "円/kWh",
  "slots": 48,                          // 実コマ数（原則48）
  "areas": {
    "北海道": [12.5, 11.05, /* …48個… */],
    "東北":   [21.0, /* … */]
    // 全9エリア
  }
}
```

48コマは「0:00〜0:30」から「23:30〜24:00」までの30分刻みです。配列の添字がそのまま時刻に対応するので、添字36なら18:00のコマになります。

価格は**税抜のエリアプライス**です。実際の電気料金には託送料金などが加わります（Storiesの脚注にも書いてあります）。

`date_raw` は日次更新の「合言葉」として使われます。ステップ⑥のPages反映確認も、Instagram側の鮮度チェックも、この値を見ています。

### `docs/history.json` — 日別の推移（最大180日）

```jsonc
{
  "dates": ["2026/08/29", "2026/08/28", /* …新しい順… */],
  "data": {
    "2026/08/29": {
      "date_label": "2026年8月29日(土)",
      "areas": { "北海道": [ /* 48コマ */ ], /* … */ }
    }
    // 日付ごとに同じ形
  }
}
```

最大180日分ですが、実際にはCSVが持っている範囲に制限されます。CSVは当年度分しかないため、**収録されるのは年度始め（4/1）から今日まで**で、それが180日を超えたぶんは切り捨てられます。年度替わりでリセットされる点は[6章](#6-データ方針過去データを推測で埋めない)を見てください。

全期間を持たせるとスマホでの初回ロードが重くなるので、年をまたぐ長期の傾向は `monthly.json` に役割を分けています。48コマ揃っていない日は収録されません。

### `docs/monthly.json` — 月平均（2022年1月〜）

```jsonc
{
  "from":   "2022-01",
  "months": ["2022-01", "2022-02", /* … */],
  "unit":   "円/kWh",
  "areas": {
    "北海道": { "2022-01": 23.6, "2022-02": 21.87, /* … */ }
    // 全9エリア
  }
}
```

毎日の実行では**当年度分だけをマージ更新**します。過去の月には一切触りません（理由は[6章](#6-データ方針過去データを推測で埋めない)）。当月は月途中でもその時点までの平均が入るので、日々値が動きます。

### `docs/.last_run` — 完了マーカー

```
2026-08-28
```

日付1行だけのテキストです。guardジョブとwatchdogの両方がこれを見ています。

繰り返しになりますが、これは**Instagram投稿まで成功した日付**であって、Web公開した日付ではありません（→ [runbook](runbook.md#3-実行時刻と監視時刻のズレ)）。

### `.ig_state.json` — Instagram投稿の進捗

```jsonc
{
  "date": "20260829",
  "posted": {
    "stories_1.png": "18131150065631711",   // 値はInstagram側のメディアID
    "stories_2.png": "18113736193770272"
    // 投稿できた分だけ増えていく
  }
}
```

3枚目で落ちた日も「2枚目まで完了」が残るので、リトライ時は3枚目から再開できます。1枚目からやり直して二重投稿する事故を防ぐためのファイルです。日付が変わるとリセットされます。

### `data/spot_summary.csv` — JEPXの生データ

JEPXからダウンロードした当年度分のCSVそのままです（cp932エンコーディング）。上記のJSONはすべてここから生成されます。

## 5. 価格アラートの判定ロジック

その日の**日内最高値**（円/kWh、税抜のエリアプライス）が、どの段階を超えたかで判定します。

| レベル | 呼称 | 目安の頻度 | 対応 |
|---|---|---|---|
| Lv1 | 高め | 月2回 | Instagram＋希望者メールのみ |
| Lv2 | 注意 | 月1回 | **ここから全顧客メール**（該当エリアのみ） |
| Lv3 | 警戒 | 年4回 | 全顧客メール＋円換算表示 |
| Lv4 | 重大 | 150円/kWh超（4年で6日） | 全顧客メール＋電話フォロー |

しきい値はエリアごとに、FY2022以降のJEPX実績から発火頻度ベースで逆算した値です。

全顧客への一斉プッシュをLv2以上に絞っているのには理由があります。軽微な値動きまで毎回メールしていると**「狼少年化」して、本当に重要なときに読まれなくなる**からです。

発火したあとの手動送信手順は [runbook](runbook.md#4-アラート発火時の手動送信手順) にあります。

### しきい値を変えたいとき

判定に使う値はすべて `scripts/alert_config.py` に集約されています。**このファイルだけを直せば、運用しながら調整できます。**

同じファイルには、Stories・Webの表示に使う5段階の `PRICE_LEVELS`（とてもおだやか〜とても高め）、「高め」帯の下限を自動導出する `HIGH_FLOOR`、円表記を統一する `yen_approx()` も定義されています。表示まわりを変えたいときも、個別スクリプトではなくここを直してください。

以前これらが各スクリプトにベタ書きされていて二重管理になっていた経緯があるので、同じ轍を踏まないよう注意してください（→ [scripts/軽微修正メモ.md](../scripts/軽微修正メモ.md)）。

## 6. データ方針：過去データを推測で埋めない

### リポジトリが持っているデータ・持っていないデータ

| データ | 中身 | 範囲 |
|---|---|---|
| `data/spot_summary.csv` | JEPXの生データ | **当年度のみ**（4/1〜今日） |
| `docs/history.json` | 日別の推移 | 上のCSVから作るので、同じく当年度のみ |
| `docs/monthly.json` | 月平均（集計済み） | **2022年1月〜**（過去年度も残る） |

過去年度のデータがまったく無いわけではありません。**月平均という集計済みの形でだけ残っています。** 無いのは過去年度の生CSV（`spot_summary_2025.csv` のようなファイル）です。

`monthly.json` の過去年度分は、以前に一度計算した結果がマージで引き継がれているものです。元になった生データはもうリポジトリにないので、**リポジトリ内のデータだけでは再計算できません。**

### 年度が替わるとhistoryは一度リセットされる

`fetch_jepx.py` は当年度のCSVをJEPXから取得して、`data/spot_summary.csv` を**丸ごと上書き**します。年度の判定は「あしたの日付」基準です。

そのため毎年 **3/31の朝**（4/1分を配信する回）に、CSVが新年度のファイルに差し替わり、前年度分が消えます。`history.json` もこれに追従するので、年間の収録日数はこう推移します。

| 時期 | `history.json` の日数 |
|---|---|
| 4月上旬 | 数日分（リセット直後） |
| 4月〜9月末 | 毎日1日ずつ増える |
| 9月末〜翌3/30 | 180日で頭打ち |
| 翌3/31 | 数日分に戻る |

**4月〜9月ごろに「180日に足りない」のは仕様です。** `--days 180` を指定していても、CSV側が年度開始以降の日数しか持っていないためで、故障ではありません。

年をまたいだ長期の傾向を見たいときは `monthly.json` を使ってください。

### 過去データを直したくなったら

**既存の数値を推測や補完で埋めてはいけません。** 手で `monthly.json` を編集するのも避けてください。

正しい手順は、JEPX公式から該当年度のCSVを取得して `data/` に置き、`build_monthly.py --rebuild` で作り直すことです。正本は常にJEPX側にあります。
