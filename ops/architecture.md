## 1. 起動の仕組み（何がきっかけで動くか）

メインの自動実行ワークフローは `.github/workflows/daily-denki-yohou.yml` です。起動元は4つあります。

| きっかけ | 実体 | 位置づけ |
|---|---|---|
| 外部cronサービス `cron-job.org` が `workflow_dispatch` を叩く | 毎朝 | **実運用の主役**。GitHubのネイティブcronは数十分単位で遅延することがあるため、時刻の正確さを外部サービスに任せている |
| GitHub Actions ネイティブ `schedule` | 10:40 / 11:10 / 11:40 JST | cron-job.orgが死んだ場合の予備（3回に分けているのも遅延対策） |
| `push`（`data/spot_summary.csv` の変更） | JEPXのCSVを手で差し替えたとき | 手動フォールバック |
| 手動 `workflow_dispatch` | 人がボタンを押す | `force=true` を付けたときだけ、ガードを無視して強制再配信できる |

**重複配信防止の仕組み**：`docs/.last_run` に「今日はもう配信した」という日付が書いてあれば、`guard` ジョブが後続処理をスキップします。これに加えて `concurrency` 設定で同時実行そのものを禁止しているため、複数のきっかけが同時に発火しても二重投稿にはなりません（[runbookの障害履歴](runbook.md#過去の障害となぜガードが多いのか)参照）。

## 2. 本体処理の流れ（ステップ⓪〜⑩）

`build-and-notify` ジョブの中身を、実行順にまとめています。番号はワークフロー内のコメント番号と対応しています。

| # | やること | 失敗したら |
|---|---|---|
| ⓪ | `fetch_jepx.py` でJEPXから最新CSVを取得 | ジョブ失敗。以降すべて止まる |
| ① | `build_prices.py --require-tomorrow` で翌日分の `prices.json` を生成 | **意図的に失敗する**（後述） |
| ①' | `build_history.py` で `history.json`（過去180日）を生成 | `continue-on-error: true`。本体は止めない |
| ①'' | `build_monthly.py` で `monthly.json`（月平均）をマージ更新 | 同上、本体は止めない |
| ② | `build_stories.py` で `stories.html` を生成 | 失敗するとPNG以降が作れず本体が止まる |
| ③ | `render_png.py` でPNG5〜6枚を書き出し | 同上 |
| ④ | 成果物を `docs/` に配置 | 同上 |
| ④-A〜D | 価格アラート判定 → Drive格納 → Slack通知 | 4ステップとも `continue-on-error: true`。ここが全滅しても本体配信は続く |
| ⑤ | `docs/` と `data/spot_summary.csv` をコミット＆push（＝GitHub Pages公開） | 本体が止まる |
| ⑥ | 公開URLの `prices.json` が今回の日付になるまでポーリング確認（最大5分） | 反映確認できないとエラー |
| ⑦ | Instagramトークンの残り日数チェック（失効14日前から警告） | お知らせのみ。失敗しても止めない |
| ⑧ | Instagram Stories へ投稿 | 失敗すると⑨のマーカーが書かれず、翌回リトライ対象になる |
| ⑧' | `.ig_state.json` に投稿済み進捗を保存 | 1枚ずつ記録するので、3枚目で落ちても4枚目からの再開になる（＝二重投稿しない） |
| ⑨ | `docs/.last_run` に本日日付を記録（＝当日完了マーカー） | **Instagram投稿の成功後にのみ**書く。ここまで来て初めて「今日は完了」扱い |
| ⑩ | Slackの #kk_でんき予報 へ日次結果通知（「☀️ 配信処理完了」＝翌日の価格レベル＋IG成否。コード上の呼び名は「安否確認」） | `if: always()` かつ `continue-on-error: true` かつ2分タイムアウト。何があっても必ず飛ばす |

**①がなぜ「意図的に失敗する」設計なのか**：`--require-tomorrow` は「CSVの最新日」ではなく「明日（JST）の行があるか」を明示的に要求します。JEPXの公表が遅れて明日分がまだCSVに無いときは、ここでエラーにして止まります。これは古いデータをうっかり配信しないためのガードで、失敗してもマーカー（⑨）は書かれないので、次のスケジュール起動が自動でリトライします。

## 3. 生成物（JSON・マーカーファイル）の中身

日々コミットされるファイルたちの構造です。「Webページはこれを読んで描画している」という関係なので、`docs/index.html` を触るときはここが実質のAPI仕様になります。

### `docs/prices.json` — 翌日分の価格（本体）

翌日1日分だけを持つ、一番重要なファイルです。48コマは「0:00〜0:30」から「23:30〜24:00」の30分刻みで、配列の添字がそのまま時刻に対応します（添字36 = 18:00コマ）。

```jsonc
{
  "date_raw":   "2026/08/29",          // 対象日（機械可読）
  "date_label": "2026年8月29日(土)",    // 表示用
  "unit":  "円/kWh",
  "slots": 48,                          // 実コマ数（原則48）
  "areas": {
    "北海道": [12.5, 11.05, /* …48個… */],
    "東北":   [21.0, /* … */]
    // 全9エリア
  }
}
```

- `date_raw` は Pages反映確認（ステップ⑥）とInstagram側の鮮度確認にも使われる、日次更新の「合言葉」です。
- 価格は**税抜のエリアプライス**。実際の電気料金には託送料金等が加わります（Storiesの脚注にも明記）。

### `docs/history.json` — 過去180日の推移（Web表示用）

```jsonc
{
  "dates": ["2026/08/29", "2026/08/28", /* …新しい順… */],
  "data": {
    "2026/08/29": {
      "date_label": "2026年8月29日(土)",
      "areas": { "北海道": [ /* 48コマ */ ], /* … */ }
    }
    // 日付ごとに同じ形
  }
}
```

- 直近180日固定です。全期間を持つとスマホの初回ロードが重くなるため、長期傾向は次の `monthly.json` に役割分担しています。
- 48コマ揃っていない日は収録されません。

### `docs/monthly.json` — 月平均くらべ（2022年1月〜）

```jsonc
{
  "from":   "2022-01",
  "months": ["2022-01", "2022-02", /* … */],
  "unit":   "円/kWh",
  "areas": {
    "北海道": { "2022-01": 23.6, "2022-02": 21.87, /* … */ }
    // 全9エリア
  }
}
```

- 毎日の実行では**当年度分だけをマージ更新**します。過去の月には一切触りません（過去改定のルールは[6章](#6-データ方針過去データを推論で埋めない)）。
- 当月が月途中でも、その時点までの平均が入ります（日々値が動く）。

### `docs/.last_run` — 当日完了マーカー

```
2026-08-28
```

日付1行だけのテキストファイルです。guardジョブとwatchdogの両方がこれを見ます。**「Instagram投稿まで成功した日付」**であって「Web公開した日付」ではない点に注意（詳細は[runbook](runbook.md#実行時刻と監視時刻のズレに注意)）。

### `.ig_state.json` — Instagram投稿の進捗（リポジトリ直下）

```jsonc
{
  "date": "20260829",
  "posted": {
    "stories_1.png": "18131150065631711",   // 値はIG側のメディアID
    "stories_2.png": "18113736193770272"
    // 公開済みの分だけ増えていく
  }
}
```

途中の枚数で失敗した日でも「どこまで投稿済みか」が残るので、リトライ時に1枚目からやり直して二重投稿する事故を防ぎます。日付が変わるとリセットされます。

### `data/spot_summary.csv` — JEPXの生データ（当年度分）

JEPXからダウンロードした電力年度分のCSVそのままです（cp932エンコーディング）。上記のJSONはすべてここから生成されます。

## 5. 価格アラートの判定ロジック

判定は「その日の日内最高値（円/kWh、税抜のエリアプライス）」がどの段階を超えたかで決まります。しきい値の実体はすべて `scripts/alert_config.py` にあり、**このファイルだけを直せば運用しながら調整できます**。

| レベル | 呼称 | 目安の頻度 | 対応 |
|---|---|---|---|
| Lv1 | 高め | 月2回（24日/年） | Instagram＋希望者メールのみ。全顧客プッシュはしない |
| Lv2 | 注意 | 月1回（12日/年） | **ここから全顧客メール**（該当エリアのみ） |
| Lv3 | 警戒 | 年4回（4日/年） | 全顧客メール＋円換算表示 |
| Lv4 | 重大 | 150円/kWh絶対値超（4年で6日のみ） | 全顧客メール＋電話フォロー |

- しきい値はエリアごとに過去5年分（FY2022〜）のJEPX実績から、発火頻度（日/年）ベースで逆算した値です。
- 「全顧客への一斉プッシュ」をLv2以上に絞っているのは、軽微な値動きまで毎回メールすると**「狼少年化」して読まれなくなる**ことを避けるためです。
- 発火後の手動送信手順（配配メール）は [runbook](runbook.md#アラート発火時の手動送信手順) にあります。

このほか `alert_config.py` には、Storiesや Webの表示に使う5段階の `PRICE_LEVELS`（とてもおだやか〜とても高め）、「高め」帯の下限を自動導出する `HIGH_FLOOR`、円表記を一元化する `yen_approx()` が定義されています。表示のしきい値や表記を変えたいときも、個別スクリプトではなくここを直してください（過去にベタ書きで二重管理していたのを一元化した経緯があるので、同じ轍を踏まないよう注意。経緯の詳細は [scripts/軽微修正メモ.md](../scripts/軽微修正メモ.md)）。

## 6. データ方針：過去データを推論で埋めない

- このリポジトリは**過去年度の生CSV（`spot_summary_YYYY.csv`）を持たない方針**です。正本はJEPX側にあります。
- `monthly.json` は通常、当年度分だけを既存ファイルにマージする「マージモード」で毎日更新されます。過去の月は上書きされません。
- 過去データの改定・作り直しが必要になった場合は、**既存の数値を推測・補完してはいけません**。必ずJEPX公式サイトから該当年度のCSVを取得し、`data/`に置いた上で `build_monthly.py --rebuild` を使って作り直してください。
